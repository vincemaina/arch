# X11 compatibility, for clients with no Wayland backend. Nothing declared here
# needs it - every application in this file is a native Wayland client - so
# Xwayland is not normally running at all. It starts on demand and exits with
# the last X11 client.
#
# READ THIS BEFORE ADDING THE FIRST X11 APPLICATION. Electron apps (VS Code,
# Discord, Slack, Obsidian, Signal), JetBrains IDEs and Java desktop apps
# generally, Steam and anything under Wine or Proton, Zoom and Teams, and
# GIMP 2.x all default to XWayland. When one arrives it will look subtly wrong
# next to everything else: GTK resolves a different icon theme under X11 than
# under Wayland, so checkmarks and dropdown arrows come out the wrong shape.
# The theme itself is fine - GTK_THEME is an environment variable and reaches
# X11 clients - it is only icons.
#
# That was investigated as TASK-42 and closed without a fix, because the impact
# is zero until such an application exists and the usual remedy is running
# xsettingsd, a daemon whose whole job would be telling X11 clients which icon
# theme to use. The ticket has the evidence and the hypothesis, which was never
# confirmed: settings.ini does set gtk-icon-theme-name and GTK reads it on both
# backends, so the XSETTINGS explanation may be wrong. Confirming it needs
# python-gobject to ask a running application what it actually resolved.
#
# Also relevant when that day comes: environment.d already carries
# _JAVA_AWT_WM_NONREPARENTING=1, and XWayland has no HiDPI - see the
# sway-capability-limits skill.
xorg-xwayland

# Clipboard HISTORY, which wl-clipboard on its own does not have: it copies and
# pastes, and the moment you copy the next thing the last one is gone.
#
# cliphist, and the choice was between two. Both are in extra, so the AUR
# question TASK-43 settled does not arise - though it does disqualify the
# usual alternatives outright: clipman, clipse and greenclip are all AUR-only
# and were not considered further.
#
#   cliphist  2.3 MiB, depends on glibc and wl-clipboard, which is already
#             above. A store and a `list`/`decode` pair, no interface of its
#             own, driven by whatever menu you point at it - which is exactly
#             the shape this desktop wants, because the menu is rofi.
#   copyq     8.7 MiB before its dependencies, and those are the cost: qt6-svg,
#             knotifications, kstatusnotifieritem, kguiaddons, qca-qt6,
#             qtkeychain-qt6 and libxtst. It draws its own Qt window, and a
#             KDE-shaped one, next to a desktop that is GTK-dark everywhere
#             else - and it wants a system tray, which this machine does not
#             have (see the network-manager-applet note above for what that
#             costs). It is also an X11-first application reaching Wayland
#             through libxtst.
#
# So cliphist for being small, headless and already dependent on what is here.
#
# It is watched by cliphist@text.service and cliphist@image.service - two
# instances, because one wl-paste watcher sees text only and would drop every
# screenshot silently. See the unit, which has the measurement.
cliphist

# Background music without a browser - TASK-101.

# firefox is the one for what qutebrowser cannot do, and the list is short but
# unavoidable: WebExtensions, and DRM. qt6-webengine ships zero Widevine files,
# so qutebrowser cannot play Netflix or anything else behind DRM at all - not a
# configuration gap, an absent codec.
#
# Firefox rather than a Chromium, and the choice is mostly made for us:
#   - brave, google-chrome and ungoogled-chromium are AUR-only, ruled out on
#     TASK-43.
#   - Arch's chromium has no Widevine either, and is larger at 416 MiB.
#   - vivaldi (434 MiB) and librewolf (424 MiB) are both bigger than firefox,
#     and librewolf is a firefox derivative that removes things in this
#     direction rather than adding them.
# That leaves firefox at 295 MiB, which enables DRM by default and fetches the
# Widevine CDM itself on first use.
firefox
